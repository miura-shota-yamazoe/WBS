## 2. 現行基本設計書のレビュー結果

### 2.1 総合評価

現行版は、採用技術、主要画面、主要機能および主要データを簡潔に把握できる。一方、実装および配布の判断に必要な設計情報が不足しているため、そのままAIへ実装を依頼すると、AI側の推測により実装方式が揺れる可能性が高い。

### 2.2 良い点

- ASP.NET Core MVC、Entity Framework Core、DBという主要技術が明記されている。
- プロジェクト管理、タスク管理、WBS管理という主要機能が整理されている。
- 画面数が少なく、初回リリースの範囲が過剰に広がっていない。
- 将来機能が初回リリースと分離されている。
- Controller、Service、Repositoryの責務分離方針が示されている。

### 2.3 主な不足点と対応方針

| No. | 指摘事項 | 影響 | 改訂方針 |
|---:|---|---|---|
| 1 | 配布形態が未定義 | 利用者がDBや実行環境を準備できない可能性がある | 初回配布版はSQLiteを標準DBとし、アプリと同梱可能な構成にする |
| 2 | PostgreSQL固定 | 個人向け配布では導入・設定の負担が大きい | DBプロバイダーを差し替え可能にし、将来の共有運用時にPostgreSQLへ移行可能にする |
| 3 | 担当者の保存方式が曖昧 | 自由入力と登録済み選択の整合が取れない | `assignees`と`tasks.assignee_name`を併用し、担当者マスタ未登録の名前も保存可能にする |
| 4 | WBS番号の採番・並び替え規則が不足 | 階層追加や削除後の番号が不定になる | 内部的には親IDと表示順を保持し、WBS番号は画面表示時に算出する |
| 5 | 完全削除時の関連データ処理が未定義 | 孤児データや誤削除が発生する | 確認ダイアログを表示し、プロジェクト削除時は配下タスクを一括削除する |
| 6 | 画面項目と画面操作が不足 | AI実装時にUI仕様を推測する必要がある | 各画面の項目、操作、遷移および表示条件を定義する |
| 7 | 検索・並び順・ページングが未定義 | 一覧の挙動が実装者ごとに変わる | 初回版の検索条件、既定順、表示方式を定義する |
| 8 | DB初期化・更新方式が未定義 | 配布後の起動やアップデートに失敗する | 初回起動時にDBを自動作成し、EF Core Migrationでスキーマを更新する |
| 9 | バックアップ方式がない | 完全削除や端末故障時に復元できない | SQLite DBファイルのバックアップ・復元機能を将来拡張として設計上考慮する |
| 10 | セキュリティ設計が不足 | Webアプリとして基本的な脆弱性対策が曖昧 | CSRF対策、入力検証、例外情報の非表示を定義する |

## 3. システム概要

### 3.1 目的

複数のプロジェクトと、その配下にあるタスクをWBS形式で管理し、担当者、期間、ステータス、優先度および進捗率を一元管理する。

### 3.2 初回リリースの利用形態

- 利用者は原則1名とする。
- ログイン機能は実装しない。
- 利用者のPC上でアプリケーションを実行する。
- データは利用者のPC内に保存する。
- 配布先でDBサーバーの構築を必要としない構成を標準とする。

### 3.3 将来の利用形態

- 複数利用者による共有利用に対応する。
- ログインおよび権限管理を追加する。
- PostgreSQLなどのサーバー型DBへ切り替える。
- Webサーバーまたはクラウド環境へ配置する。

## 4. システム構成

### 4.1 採用技術

| 項目 | 初回リリース | 将来構成 |
|---|---|---|
| アプリケーション方式 | ASP.NET Core MVC | ASP.NET Core MVC |
| 言語 | C# | C# |
| UI | Razor View、HTML、CSS、JavaScript | 同左 |
| ORM | Entity Framework Core | Entity Framework Core |
| DB | SQLite | PostgreSQL |
| IDE | Visual Studio | Visual Studio |
| バージョン管理 | Git / GitHub | Git / GitHub |
| 配布方式 | Windows向け自己完結型またはフレームワーク依存型発行 | Webサーバー配置を追加 |

### 4.2 DB選定方針

初回配布版の標準DBはSQLiteとする。

SQLiteを採用する理由は以下のとおりである。

- DBサーバーのインストールが不要である。
- 接続先、ユーザー名、パスワードなどの初期設定が不要である。
- DBファイルをアプリケーション用データフォルダーに保存できる。
- 個人利用規模では十分な性能を確保できる。
- バックアップ時はDBファイルをコピーできる。

将来の複数人利用では、同一SQLiteファイルのネットワーク共有は行わず、PostgreSQLへ移行する。

### 4.3 DB切り替え方式

DB固有処理をControllerおよびViewに記述しない。データアクセスはEntity Framework Coreを通じて行い、設定ファイルによってDBプロバイダーを切り替えられる構成を目標とする。

```text
Browser
  │
ASP.NET Core MVC
  ├─ Controller
  ├─ Service
  ├─ Repository / DbContext
  │
Entity Framework Core
  ├─ SQLite（初回配布版）
  └─ PostgreSQL（将来の共有版）
```

### 4.4 レイヤー構成

| レイヤー | 主な責務 |
|---|---|
| View | 表示、入力、クライアント側の補助処理 |
| Controller | リクエスト受付、入力モデル検証、Service呼び出し、画面遷移 |
| Service | 業務ルール、WBS操作、トランザクション制御 |
| Repository / DbContext | DB検索、登録、更新、削除 |
| Domain / Entity | データ構造および基本的な状態表現 |
| ViewModel | 画面入出力専用データ |

## 5. 配布および実行方式

### 5.1 初回配布方式

- Windows PC向けに発行する。
- 利用者がDBサーバーを準備しなくても起動できること。
- 初回起動時にSQLite DBファイルが存在しない場合は自動作成すること。
- 必要なテーブルおよび初期データはEF Core Migrationにより作成すること。
- 接続文字列および保存先は設定ファイルから変更可能とすること。

### 5.2 DBファイル保存先

DBファイルはアプリケーション本体の配置フォルダーへ直接保存せず、利用者ごとの書き込み可能なデータフォルダーへ保存する。

推奨例：

```text
%LOCALAPPDATA%/WbsApp/Data/wbsapp.db
```

### 5.3 更新時の考慮

- アプリケーション更新時に既存DBファイルを削除しない。
- 起動時に未適用Migrationを確認し、必要なDB更新を実行する。
- Migration失敗時はアプリを継続起動せず、利用者向けエラーを表示する。
- DB構造を破壊する変更を行う場合は、バックアップ手順をREADMEへ記載する。

## 10. WBS設計

### 10.1 階層管理

- タスクは`ParentTaskId`による自己参照で階層を表現する。
- ルートタスクの`ParentTaskId`はNULLとする。
- 階層数にはアプリケーション上の固定上限を設けない。
- 循環参照は禁止する。

### 10.2 表示順

- 各タスクは同一親配下における`SortOrder`を保持する。
- `SortOrder`は1以上の整数とする。
- 並び替え時は同一親配下の`SortOrder`を再採番する。

### 10.3 WBS番号

WBS番号はDBへ固定文字列として保存せず、親子関係と`SortOrder`から画面表示時に算出する。

例：

```text
1
1.1
1.2
1.2.1
2
```

この方式により、タスクの追加、削除および並び替え後も番号の整合性を維持する。

### 11.4 DB互換性方針

- 主キーはDBの自動連番に依存せず、アプリケーションで生成するUUIDを基本とする。
- SQLiteとPostgreSQLで扱いが異なるDB固有型の利用を避ける。
- 日付は`DateOnly`相当、日時はUTCを基本として保存する。
- 列名、制約名およびインデックス名は英数字で定義する。
- ステータスおよび優先度はアプリケーション側Enumで管理し、DBには文字列または整数として保存する。実装時に方式を統一する。

## 12. リレーションおよび削除規則

| 親 | 子 | 関係 | 削除時の処理 |
|---|---|---|---|
| projects | tasks | 1対多 | プロジェクト削除時に配下タスクを一括削除 |
| tasks | tasks | 1対多の自己参照 | 親タスク削除時に子孫タスクを一括削除 |
| assignees | tasks | 直接の外部キー関係なし | 担当者候補削除後もタスク上の担当者名を保持 |

完全削除は要件どおり採用するが、すべての削除操作に確認ダイアログを設ける。

---

## 13. 検索および一覧表示方式

### 13.1 プロジェクト一覧

- 検索条件：プロジェクト名、状態
- 既定順：更新日時降順
- 初回リリースでは最大表示件数を100件とし、超過時はページングする。

### 13.2 WBS一覧

- 検索条件：タスク名、担当者、ステータス、優先度、遅延有無
- 既定順：WBS順
- 検索時は一致したタスクのみでなく、階層を把握できるよう祖先タスクも表示対象に含める。
- 大量データ対策として、初回は1プロジェクトあたり5,000タスク程度を設計上の目安とする。

---

## 14. 入力検証

| 対象 | 検証内容 |
|---|---|
| プロジェクト名 | 必須、1～100文字 |
| プロジェクト期間 | 開始予定日が終了予定日以前であること |
| タスク名 | 必須、1～200文字 |
| タスク期間 | 開始予定日が終了予定日以前であること |
| 進捗率 | 0～100の整数 |
| ステータス | 定義済み値のいずれか |
| 優先度 | 定義済み値のいずれか |
| 担当者候補名 | 必須、1～100文字、重複不可 |
| 親タスク | 同一プロジェクト内であること、自分自身および子孫ではないこと |

入力検証はクライアント側のみへ依存せず、サーバー側で必ず実施する。

---

## 15. トランザクション設計

以下の処理はトランザクション内で実行する。

- プロジェクトと配下タスクの削除
- タスクと子孫タスクの削除
- タスク並び替えおよび`SortOrder`再採番
- 親タスク変更に伴う旧階層、新階層双方の再採番
- Migrationおよび初期データ登録

処理途中で例外が発生した場合はロールバックする。

---

## 16. エラー処理

### 16.1 入力エラー

- 対象項目の近くにエラーメッセージを表示する。
- 入力済みの内容を保持する。

### 16.2 業務エラー

- 削除済みデータの更新など、処理を継続できない場合は利用者向けメッセージを表示する。
- 並び替え競合などが発生した場合は再読み込みを案内する。

### 16.3 システムエラー

- 詳細な例外情報およびスタックトレースを利用者画面へ表示しない。
- ログへ日時、処理、例外情報を記録する。
- 共通エラー画面へ遷移する。

---

## 17. セキュリティ設計

初回はログイン機能を持たないが、Webアプリとして以下を実施する。

- 登録、更新、削除処理にCSRF対策を適用する。
- Razorの標準エスケープを利用し、XSSを防止する。
- SQLを文字列連結で生成せず、EF Coreを利用する。
- 入力値をサーバー側で検証する。
- 本番環境では詳細例外画面を無効化する。
- 外部公開を前提とせず、初回版はローカルホストでの利用を標準とする。

## 18. ログ設計

| ログ種別 | 内容 |
|---|---|
| 情報 | アプリ起動、DB初期化、Migration適用 |
| 警告 | 入力不正、対象データなし、競合 |
| エラー | DB接続失敗、Migration失敗、未処理例外 |

ログへタスクの説明や備考など、不要な利用者入力全文を出力しない。

## 19. 非機能設計

### 19.1 性能

- 通常の一覧表示および更新処理は3秒以内を目標とする。
- 一覧検索に使用する列へ必要なインデックスを設定する。
- 不要な全件取得を避ける。

### 19.2 保守性

- Controllerに業務ロジックを集中させない。
- 画面用モデルとDB Entityを分離する。
- 列挙値、文字数制限およびメッセージを可能な範囲で共通化する。
- DB Migrationをソース管理対象とする。

### 19.3 可搬性

- 初回版はWindowsでの利用を保証対象とする。
- DBアクセスをEF Coreへ集約し、SQLiteからPostgreSQLへ移行しやすくする。
- DBファイルの保存先を設定可能とする。

### 19.4 データ保全

- DB更新はトランザクションを使用する。
- アプリ更新時に既存DBを削除しない。
- 将来、画面からバックアップおよび復元を行える構造を考慮する。
