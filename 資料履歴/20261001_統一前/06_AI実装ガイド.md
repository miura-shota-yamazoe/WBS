# WBSアプリ AI実装ガイド

## 1. 目的

本書は、AIコーディングエージェント（Codex / Claude Code など）が、WBSアプリを一貫した方針で実装するためのルールを定義する。

AIは本書だけで判断せず、以下の設計書を優先順位順に参照すること。

1. 要件定義書
2. 基本設計書
3. DB設計書
4. 画面設計書
5. 本書

設計書間に矛盾がある場合は、勝手に仕様を決めず、該当箇所を明示して確認すること。

## 3. 実装方針

### 3.1 基本方針

- 設計書に記載されていない機能を独自判断で追加しない
- 1回の作業で大規模な変更を行わない
- 機能単位で実装、ビルド、テストを行う
- 既存コードの構成と命名規則を優先する
- 動作している既存機能を不用意に変更しない
- 仮実装や未使用コードを残さない
- 警告を可能な限り解消する
- エラーを握りつぶさない
- 配布先でDBサーバーの設定を必要としない構成とする

### 3.2 初回リリース対象外

以下は初回リリースでは実装しない。

- ログイン機能
- 権限管理
- Web API
- ガントチャート
- ドラッグ＆ドロップによる並び替え
- Excel入出力
- コメント
- 添付ファイル
- 通知
- スマートフォン専用UI

## 5. レイヤー責務

### 5.1 Controller

Controllerは次の責務のみを持つ。

- HTTPリクエストの受け取り
- 入力値の検証結果確認
- Serviceの呼び出し
- ViewModelの受け渡し
- 画面遷移
- 成功・失敗メッセージの設定

Controllerに以下を記述しない。

- 複雑な業務ロジック
- 直接的なDB操作
- WBS番号算出処理
- 並び替えロジック
- 削除対象階層の探索
- 長い例外処理

### 5.2 Service

Serviceは業務ロジックを担当する。

- プロジェクト管理
- タスク管理
- WBS階層管理
- WBS番号算出
- 並び替え
- 階層変更
- 遅延判定
- 進捗率集計
- 削除前の影響範囲確認
- トランザクション制御

### 5.3 Repository

Repositoryは永続化処理を担当する。

- Entity Framework CoreによるCRUD
- 条件検索
- 関連データ取得
- データ保存
- 削除
- 排他制御に必要なデータ取得

Repositoryに業務判断を記述しない。

### 5.4 ViewModel

画面入力・表示にはEntityを直接使用せず、原則としてViewModelを使用する。

ViewModelには次を含める。

- 画面入力項目
- 表示用の加工済み値
- 選択肢
- バリデーション属性
- 一覧用データ

## 6. 命名規則

| 対象 | ルール | 例 |
|---|---|---|
| クラス | PascalCase | `ProjectService` |
| メソッド | PascalCase | `CreateProjectAsync` |
| 非同期メソッド | `Async`を付与 | `GetTasksAsync` |
| ローカル変数 | camelCase | `projectId` |
| privateフィールド | `_camelCase` | `_projectRepository` |
| インターフェース | `I`を付与 | `IProjectService` |
| ViewModel | `ViewModel`を付与 | `ProjectEditViewModel` |
| DTO | 必要な場合のみ`Dto` | `TaskTreeDto` |
| 定数 | PascalCase | `DefaultPageSize` |

略語を多用せず、用途が理解できる名称を使用する。

## 7. C#実装ルール

- Nullable Reference Typesを有効にする
- `var`は型が明確な場合に使用する
- 非同期処理では`async` / `await`を使用する
- DBアクセスは原則として非同期メソッドを使用する
- `CancellationToken`を可能な範囲で受け渡す
- `DateTime.Now`の乱用を避け、日時取得処理を集約する
- 列挙値は文字列ではなくEnumで管理する
- Magic Number、Magic Stringを避ける
- メソッドは1つの責務に限定する
- 長大なメソッドは分割する
- コメントは「何をしているか」ではなく「なぜ必要か」を記述する
- 不要な`try-catch`を追加しない
- 例外を空のcatchで握りつぶさない

## 8. Entity Framework Coreルール

### 8.1 DBプロバイダー

初回配布版ではSQLiteを使用する。

将来PostgreSQLへ移行できるよう、SQLite固有のSQLや関数への依存を最小限にする。

### 8.2 DbContext

- DbContextはDIコンテナから取得する
- Controllerで直接DbContextを使用しない
- Entity設定は可能な限りFluent APIへ分離する
- テーブル名、列名、制約を明示する
- 日付・日時の保存形式を統一する

### 8.3 Migration

- DB変更はMigrationとして管理する
- 既存Migrationを安易に書き換えない
- Migration名は変更内容が分かる名称とする
- 初回起動時に未適用Migrationを適用できる構成とする
- Migration失敗時はログへ記録する
- 更新前のバックアップ方針を考慮する

### 8.4 トランザクション

以下の処理はトランザクションを使用する。

- プロジェクトと関連タスクの削除
- 親タスクと子タスクの一括削除
- タスク並び替え
- タスク階層変更
- 複数レコードの表示順更新

## 9. DB実装ルール

### 9.1 WBS番号

WBS番号はDBへ固定保存しない。

次の情報から表示時に算出する。

- `parent_task_id`
- `sort_order`
- タスク階層

例：

```text
1
1.1
1.2
1.2.1
2
```

### 9.2 タスク階層

- 最上位タスクの`parent_task_id`はNULLとする
- 自分自身を親に設定してはならない
- 子孫タスクを親に設定してはならない
- 循環参照を禁止する
- 階層数にアプリケーション上の固定上限を設けない

### 9.3 表示順

- 同一親配下で`sort_order`を管理する
- 追加時は同一階層の末尾へ追加する
- 削除後は必要に応じて連番へ再整理する
- 並び替え処理はServiceで行う

### 9.4 削除

本アプリは完全削除を採用する。

- プロジェクト削除時は配下タスクも削除する
- 親タスク削除時は子孫タスクも削除する
- 削除前に影響範囲を画面へ表示する
- 担当者候補を削除しても既存タスクの担当者名は保持する

## 10. バリデーションルール

### 10.1 基本方針

- クライアント側とサーバー側の両方で検証する
- サーバー側検証を必須とする
- エラー時は入力値を保持する
- 項目ごとに具体的なメッセージを表示する
- DB制約だけに依存しない

### 10.2 プロジェクト

- プロジェクト名：必須、100文字以内
- 説明：1000文字以内
- 開始予定日：必須
- 終了予定日：必須
- 終了予定日：開始予定日以降

### 10.3 タスク

- タスク名：必須、200文字以内
- 担当者名：100文字以内
- 開始予定日：必須
- 終了予定日：必須
- 終了予定日：開始予定日以降
- 進捗率：0〜100の整数
- ステータス：必須
- 優先度：必須
- 備考：2000文字以内

### 10.4 担当者

- 担当者名：必須、100文字以内
- 前後の空白を除去する
- 同名担当者の重複登録を防止する

## 11. 画面実装ルール

### 11.1 共通UI

- 画面設計書に定義したレイアウトを優先する
- ヘッダー、サイドメニュー、ボタン配置を統一する
- 主要ボタンは青系
- 削除ボタンは危険操作として明確に区別する
- 色だけで状態を表現しない
- 必須項目を明示する
- 入力エラーは対象項目の直下に表示する
- 成功メッセージは画面上部に表示する
- 空データ時は次に行う操作を案内する
- 一覧はPCブラウザで見やすく表示する
- WBS一覧は必要に応じて横スクロールを許可する

### 11.2 削除確認

削除対象と影響範囲を確認ダイアログへ表示する。

削除ボタンを初期フォーカスにしない。

### 11.3 二重送信防止

登録・更新処理中はボタンを無効化し、処理中であることを表示する。

### 11.4 未保存変更

登録・編集画面で入力変更後に離脱する場合は確認を表示する。

## 12. ステータス・優先度

### 12.1 ステータス

```text
未着手
作業中
レビュー中
完了
```

### 12.2 優先度

```text
高
中
低
```

文字列を直接比較せず、Enumとして定義する。

### 12.3 遅延判定

以下をすべて満たす場合に遅延と判定する。

- 終了予定日が現在日より前
- ステータスが完了ではない

## 13. エラー処理

### 13.1 基本方針

- 利用者へ内部例外情報を表示しない
- SQL、スタックトレース、ファイルパスを画面へ出さない
- 予期しない例外はログへ記録する
- エラーIDを発行し、画面とログで照合可能にする
- 保存失敗時は可能な限り入力内容を保持する

### 13.2 想定エラー

- 対象データが存在しない
- DB更新競合
- DBファイルアクセス失敗
- Migration失敗
- 入力値不正
- 循環参照となる階層変更
- 並び替え対象が存在しない

---

## 14. ログ出力

### 14.1 出力対象

- アプリケーション起動
- DB初期化
- Migration適用
- 予期しない例外
- DB保存失敗
- 削除失敗
- 階層変更失敗
- 並び替え失敗

### 14.2 ログへ含めない情報

- パスワード
- 認証トークン
- 個人情報の過剰な出力
- SQLパラメーターの不用意な完全出力

初回版にはログイン機能がないが、将来拡張を考慮する。

## 15. セキュリティ

- POST処理にはCSRF対策を適用する
- Razorの自動エスケープを無効化しない
- HTMLを直接出力する処理を最小限にする
- 入力値をSQL文字列へ連結しない
- Entity Framework Coreのパラメーター化を利用する
- 本番環境で詳細例外画面を表示しない
- 配布用設定に開発用の秘密情報を含めない

## 17. AIの作業手順

AIは機能ごとに次の手順で作業する。

1. 関連する設計書を読む
2. 対象機能と影響範囲を整理する
3. 既存コードを確認する
4. 実装方針を決める
5. 必要最小限のファイルを変更する
6. ビルドする
7. テストを実行する
8. エラーと警告を確認する
9. 問題があれば修正する
10. 変更内容を要約する

一度に複数の大機能を実装しない。

## 19. AIへの禁止事項

- 設計書を無視して仕様を変更しない
- PostgreSQL固定の実装にしない
- Controllerから直接DBへアクセスしない
- WBS番号を固定値としてDBへ保存しない
- タスク階層に固定上限を設けない
- 削除を論理削除へ勝手に変更しない
- ログイン機能を初回版へ追加しない
- APIを不要に追加しない
- 大量のファイルを理由なく変更しない
- 動作確認なしで完了扱いにしない
- テスト失敗を無視しない
- 既存Migrationを勝手に削除しない
- 秘密情報や個人環境のパスをコミットしない
- 仮データやデバッグコードを残さない

## 20. AI作業完了時の報告形式

AIは作業完了時に以下を報告する。

```md
## 実装結果

### 実装した内容

- 実装内容1
- 実装内容2

### 変更ファイル

- `path/to/file1`
- `path/to/file2`

### ビルド結果

- 成功 / 失敗
- 警告件数

### テスト結果

- 実行したテスト
- 成功件数
- 失敗件数

### 未対応・注意事項

- 未対応事項
- 追加確認が必要な事項
```

## 21. 完了条件

以下をすべて満たした場合のみ、対象機能を完了とする。

- 設計書どおりに実装されている
- ビルドが成功する
- 対象テストが成功する
- 重大な警告が残っていない
- エラー時の動作が確認されている
- 既存機能が破壊されていない
- 変更内容が報告されている
- 配布版のSQLite環境で動作する
