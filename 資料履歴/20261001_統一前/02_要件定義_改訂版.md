## 2. システム概要

### 2.1 システム名称

WBSアプリ

### 2.2 開発目的

複数のプロジェクトと、その配下にあるタスクをWBS形式で管理し、担当者、期間、ステータス、優先度および進捗率を一元管理できるWebアプリケーションを開発する。

### 2.3 解決する課題

- プロジェクトごとの作業内容を階層的に整理できない。
- タスクの担当者、期限、進捗および優先度を一か所で確認しにくい。
- タスクの親子関係や実施順序を分かりやすく管理したい。
- 個人利用から開始し、完成度が高い場合は他の利用者へ配布したい。

### 2.4 開発方針

- 初回リリースは個人利用を対象とする。
- 初回リリースではログイン機能を実装しない。
- Windows PCへ配布しやすい構成とする。
- 配布先でDBサーバーの構築を必要としないことを基本とする。
- AI（Codex、Claude Code等）を活用して実装する。
- 将来的な複数人利用およびサーバー型DBへの移行を考慮する。

---

## 3. 利用者および利用形態

### 3.1 初回リリース

- 主な利用者は1名とする。
- 利用者のWindows PC上でアプリケーションを実行する。
- ログインせずに利用できる。
- データは利用者のPC内に保存する。
- インターネット接続がない状態でも、基本機能を利用できることを目標とする。

### 3.2 配布時

- アプリケーションを他の利用者へ配布できること。
- 配布先でPostgreSQL等のDBサーバーを別途インストールしなくても利用できること。
- アプリケーションの初回起動時に、必要なDBおよびテーブルを作成できること。
- アプリケーション更新時に既存データを引き継げること。

### 3.3 将来利用

- 複数人による同時利用を想定する。
- ログイン、ユーザー管理および権限管理を追加できること。
- サーバー型DBへ移行できる構成とする。
- Webサーバーまたはクラウド環境への配置を可能とする。

| 言語 | C# | C# |

### 4.1 DB要件

- 初回リリースの標準DBはSQLiteとする。
- DBファイルは利用者ごとの書き込み可能なフォルダーへ保存する。
- アプリケーション本体の更新時に既存DBファイルを削除しない。
- 初回起動時にDBが存在しない場合は自動作成する。
- DB構造の更新はEntity Framework Core Migration等で管理する。
- 将来、PostgreSQLへ移行しやすいデータアクセス構成とする。
- SQLiteのDBファイルをネットワーク共有して複数人で同時利用する方式は採用しない。

## 6. 機能要件

## 6.1 プロジェクト管理

### 6.1.1 プロジェクト一覧

- 登録済みプロジェクトを一覧表示できること。
- プロジェクト名および状態で検索できること。
- 一覧からプロジェクトのWBS画面へ遷移できること。
- 一覧からプロジェクトの編集および削除を実行できること。

### 6.1.2 プロジェクト登録

以下の情報を登録できること。

| 項目 | 必須 | 要件 |
|---|:---:|---|
| プロジェクト名 | ○ | 1～100文字 |
| 説明 | - | 最大1000文字 |
| 開始予定日 | ○ | 日付形式 |
| 終了予定日 | ○ | 開始予定日以降 |
| 状態 | ○ | 進行中、完了 |

### 6.1.3 プロジェクト編集

- 登録済みプロジェクトの情報を編集できること。
- 入力エラーがある場合は更新せず、入力内容を保持してエラーを表示すること。

### 6.1.4 プロジェクト削除

- プロジェクトを完全削除できること。
- 削除前に確認を求めること。
- プロジェクト削除時は、配下のタスクも削除対象となることを明示すること。
- プロジェクトと配下タスクを一括して削除し、途中失敗時は削除前の状態へ戻すこと。

---

## 6.2 タスク管理

### 6.2.1 タスク一覧

- 選択したプロジェクトのタスクをWBS形式で一覧表示できること。
- 親子関係が分かる階層表示とすること。
- タスク名、担当者、ステータス、優先度および遅延有無で絞り込めること。
- タスクの追加、子タスク追加、編集、削除および並び替えを実行できること。

### 6.2.2 タスク登録

以下の情報を登録できること。

| 項目 | 必須 | 要件 |
|---|:---:|---|
| 親タスク | - | ルートタスクの場合は未指定 |
| タスク名 | ○ | 1～200文字 |
| 担当者 | - | 自由入力または登録済み候補から選択 |
| 開始予定日 | ○ | 日付形式 |
| 終了予定日 | ○ | 開始予定日以降 |
| 進捗率 | ○ | 0～100の整数 |
| ステータス | ○ | 未着手、作業中、レビュー中、完了 |
| 優先度 | ○ | 高、中、低 |
| 備考 | - | 最大2000文字 |

### 6.2.3 タスク編集

- 登録済みタスクの情報を編集できること。
- 親タスクを変更できること。
- 自分自身または自分の子孫を親タスクとして指定できないこと。
- 別プロジェクトのタスクを親として指定できないこと。

### 6.2.4 タスク削除

- タスクを完全削除できること。
- 削除前に確認を求めること。
- 子タスクを持つ場合は、子孫タスクも削除対象となることを明示すること。
- タスクおよび子孫タスクの削除は一括処理とすること。

### 6.2.5 タスク並び替え

- 同一階層内でタスクの表示順を変更できること。
- 初回リリースでは、上へ移動および下へ移動の操作に対応すること。
- ドラッグ＆ドロップによる並び替えは必須としない。

---

## 6.3 WBS管理

### 6.3.1 階層管理

- タスクは親子関係を持てること。
- 階層数に固定上限を設けないこと。
- 循環する親子関係を登録できないこと。

### 6.3.2 WBS番号

- WBS番号は自動採番すること。
- WBS番号は親子関係および同一階層内の表示順から生成すること。
- タスクの追加、削除、移動および並び替え後も番号の整合性を保つこと。

例：

```text
1
1.1
1.2
1.2.1
2
```

### 6.3.3 階層表示

- 子タスクは親タスクよりも字下げして表示すること。
- タスク階層を折りたたみ、展開できること。
- 検索結果を表示する際は、対象タスクの位置を把握できるよう必要な祖先タスクも表示すること。

---

## 6.4 進捗管理

### 6.4.1 ステータス

以下の値を使用する。

| 値 |
|---|
| 未着手 |
| 作業中 |
| レビュー中 |
| 完了 |

### 6.4.2 進捗率

- 0～100の整数で管理すること。
- 進捗率が100の場合はステータスを完了とすること。
- ステータスを完了にした場合は進捗率を100とすること。

### 6.4.3 優先度

以下の値を使用する。

| 値 |
|---|
| 高 |
| 中 |
| 低 |

### 6.4.4 遅延判定

以下の条件をすべて満たすタスクを遅延として扱う。

- 終了予定日が現在日より前である。
- ステータスが完了ではない。

遅延タスクは一覧上で判別できる表示とすること。

---

## 6.5 担当者管理

### 6.5.1 担当者入力

- タスク登録および編集時に担当者名を直接入力できること。
- 登録済み担当者を候補一覧から選択できること。
- 候補一覧に存在しない担当者名も保存できること。

### 6.5.2 担当者候補管理

- 担当者候補を登録、編集および削除できること。
- 同一名称の重複登録を防止すること。
- 担当者候補を削除しても、既存タスクに保存済みの担当者名は変更しないこと。

---

## 6.6 DB初期化および更新

- 初回起動時に必要なDBファイル、テーブルおよび初期データを作成できること。
- アプリケーション更新時に必要なDB構造の変更を適用できること。
- DB更新に失敗した場合は通常利用を継続せず、利用者へエラーを表示すること。
- DB更新によって既存データを不用意に削除しないこと。

## 8. データ要件

### 8.1 プロジェクト

以下の情報を保持する。

- プロジェクトID
- プロジェクト名
- 説明
- 開始予定日
- 終了予定日
- 状態
- 作成日時
- 更新日時

### 8.2 タスク

以下の情報を保持する。

- タスクID
- プロジェクトID
- 親タスクID
- 同一階層内の表示順
- タスク名
- 担当者名
- 開始予定日
- 終了予定日
- 進捗率
- ステータス
- 優先度
- 備考
- 作成日時
- 更新日時

### 8.3 担当者候補

以下の情報を保持する。

- 担当者ID
- 担当者名
- 作成日時
- 更新日時

### 8.4 データ保持方針

- データ削除は完全削除とする。
- WBS番号は固定値として保持せず、階層および表示順から算出することを基本とする。
- 主キーは将来のDB移行を考慮した方式とする。
- 日時情報は環境差異を考慮して保存する。
- 担当者候補とタスクの担当者名は独立して保持し、候補削除後もタスク情報を維持する。

## 9. 非機能要件

## 9.1 性能

- 通常の一覧表示、検索、登録、更新および削除は3秒以内を目標とする。
- 1プロジェクトあたり5,000タスク程度までを設計上の目安とする。
- プロジェクト一覧は100件を超える場合にページングできること。
- 不要な全件データ取得を避けること。

## 9.2 可用性

- DBサーバーを別途構築しなくても初回版を利用できること。
- DBが未作成の場合でも、初回起動処理により利用開始できること。
- DB更新に失敗した場合は、データ破損を避けるため処理を中断すること。

## 9.3 保守性

- 機能単位で責務を分離すること。
- 業務処理と画面表示処理を分離すること。
- DBアクセスを一か所に集約すること。
- DB構造の変更履歴をソース管理すること。
- AIが読み取りやすい命名、構成およびドキュメントを維持すること。

## 9.4 可搬性および配布性

- 初回版はWindows PCで利用できること。
- 配布先でDBサーバーの構築を必要としないこと。
- 利用者が書き込み可能なフォルダーへデータを保存すること。
- アプリ更新時に既存データを引き継げること。
- 将来、PostgreSQLへ切り替えやすい構成とすること。

## 9.5 セキュリティ

初回リリースではログイン機能を持たないが、以下を満たすこと。

- 初回版はローカルホストでの利用を標準とする。
- 登録、更新および削除処理にCSRF対策を行うこと。
- 入力内容をサーバー側で検証すること。
- 画面表示時にXSS対策を行うこと。
- SQLを文字列連結で生成しないこと。
- 本番利用時に詳細な例外情報を画面へ表示しないこと。

## 9.6 データ保全

- 関連する複数データの更新および削除は一括処理とすること。
- 処理途中で失敗した場合は、処理前の状態へ戻すこと。
- アプリ更新時に既存DBを削除しないこと。
- 将来的なバックアップおよび復元機能を追加できる構成とすること。

## 9.7 ログ

- アプリ起動、DB初期化、DB更新およびシステムエラーを記録できること。
- エラー調査に必要な情報を記録すること。
- 利用者が入力した説明や備考の全文を不要にログ出力しないこと。

| No. | 対象 | ルール |

| 10 | 削除 | 完全削除とし、削除前に確認を求める |
| 11 | 遅延 | 期限超過かつ未完了の場合に遅延とする |

## 11. 制約事項

- 初回リリースではログイン機能を実装しない。
- 初回リリースでは複数人同時利用を保証しない。
- 初回リリースではSQLiteを使用する。
- SQLite DBファイルを共有フォルダーへ配置して複数人利用しない。
- データ削除は論理削除ではなく完全削除とする。
- ガントチャートは初回リリース対象外とする。
- 初回リリースはWindows環境を保証対象とする。

## 13. 受入条件

### 13.1 機能

- 複数のプロジェクトを登録、表示、検索、編集および削除できること。
- プロジェクトごとに複数のタスクを登録、表示、検索、編集および削除できること。
- タスクを階層化し、WBS番号を自動表示できること。
- 階層数に固定上限を設けず、複数階層のタスクを登録できること。
- 同一階層内でタスクを並び替えできること。
- ステータス、優先度、進捗率および担当者を管理できること。
- 担当者名を直接入力し、登録済み候補からも選択できること。
- 遅延タスクを判別および絞り込みできること。
- プロジェクト削除時に配下タスクも削除されること。
- 親タスク削除時に子孫タスクも削除されること。

### 13.2 配布およびDB

- 配布先でDBサーバーを構築せずに起動できること。
- 初回起動時にSQLite DBおよび必要なテーブルを自動作成できること。
- アプリケーション更新後も既存データを利用できること。
- DB更新失敗時にデータを破損させず、利用者へエラーを表示できること。

### 13.3 品質

- 定義した入力チェックがサーバー側で動作すること。
- 通常操作で未処理例外が発生しないこと。
- 予期しないエラー発生時に詳細な内部情報を画面へ表示しないこと。
- ビルドエラーおよび重大な警告がないこと。
- READMEに記載された手順で起動できること。
- 主要機能に対するテストが実施され、期待結果を満たすこと。
